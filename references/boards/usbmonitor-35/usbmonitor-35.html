Overview

The UsbMonitor is a 3.5 inch display of 320 x 480 pixels in portrait orientation. A host program fills the panel with RGB565 frames through a USB 2.0 CDC-ACM serial port. The unit reports the product string UsbMonitor and the identifiers 1a86:5722, and it speaks revision A of the protocol that the open source turing-smart-screen-python library implements.

How it communicates

The host program writes six-byte command packets and pixel bytes to the serial port. The command values and the packet layout come from the open source drivers in section 9. The unit answered HELLO every time it was sent.

Command packet

Each command is six bytes. The first four bytes pack four 10-bit coordinates. The last byte is the command code.

b0 = x >> 2
b1 = (x & 3) << 6 | y >> 4
b2 = (y & 15) << 4 | ex >> 6
b3 = (ex & 63) << 2 | ey >> 8
b4 = ey & 255
b5 = command

(x, y) is the top-left corner and (ex, ey) the bottom-right corner, both inclusive. A packet has no length field, no checksum and no terminator. The firmware reads one command from the start of a USB transfer and ignores the rest of that transfer.

SET_ORIENTATION is 16 bytes: the packet, then 100 + orientation, the width 01 40 and the height 01 e0 big-endian, and five zero bytes. Portrait is 100.

For SET_BRIGHTNESS, the value is in the x field: int(255 - level / 100 * 255). Value 0 is the brightest. Value 255 is the darkest. Level 80 gives 51.

HELLO exchange

Send 45 45 45 45 45 45. The unit answers 01 01 01 01 01 01 for the UsbPCMonitor 3.5 at 320 x 480. A reply other than that identifies a different model and stops the send before any other byte.

Frame

A full frame is 320 x 480 pixels at two bytes per pixel, 307200 bytes. The bitmap header is 00 00 04 fd df c5. The pixel bytes follow the header. Each pixel is RGB565 little-endian: (r >> 3) << 11 | (g >> 2) << 5 | b >> 3, low byte first. Pixels run row-major from the top-left corner.

The working pauses are 50 ms after SET_ORIENTATION and after SET_BRIGHTNESS, and 20 ms after the bitmap header.

Power

The power source is not recorded. No battery is recorded. The power source and the current draw are untested.

Quick start

The sequence below is a generic serial exchange. The observed exchange used a serial port at 115200 baud, 8 data bits, no parity, 1 stop bit and no flow control.

  1. Open the serial port at 115200 baud, 8N1, with no flow control.
  2. Write 45 45 45 45 45 45. Read six bytes. Expect 01 01 01 01 01 01 within 1.5 s.
  3. Write 00 00 00 00 00 79 64 01 40 01 e0 00 00 00 00 00 (portrait) and wait 50 ms.
  4. Write 0c c0 00 00 00 6e (brightness level 80) and wait 50 ms.
  5. Write 00 00 04 fd df c5 (bitmap header) and wait 20 ms.
  6. Write 307200 RGB565 little-endian pixel bytes in 2560-byte writes, with 20 ms after each write.

The send writes 307234 bytes in 124 writes. Write each part alone. The bitmap header does not share a write with pixel bytes.

The observed wrap

  • The send that showed the wrap wrote 307235 bytes for a 307234-byte stream.
  • Its bitmap header shared a write with the first pixel bytes.
  • A byte-exact re-send of the same frame showed the same image until the unit was power-cycled.
  • After the power cycle, the send in section 6 wrote 307234 bytes and HELLO was answered 01 01 01 01 01 01.
  • The user did not report whether the send in section 6 removed the wrap. That result is untested.
  • The cause is untested: a desynchronised panel, or a fixed line offset in this unit's firmware.
  • The 40-pixel figure is an estimate from a photo, plus or minus 10 pixels.

Firmware and tooling

The panel runs closed vendor firmware, UsbPCMonitor. Its source is not available. No update path is recorded.

The vendor application binaries are published. The .NET IL of the application was unreadable and its library is UPX-compressed, so no command bytes were recovered from them. The protocol comes from open source host drivers.

  • turing-smart-screen-python revision A implements the protocol. Auto-detect matches the serial string USB35INCHIPSV2 or the identifiers 1a86:5722.
  • ch340disp is a C driver for the same unit, with the same packing and HELLO reply table.
  • turing-smart-screen is a Rust driver with the same command values.

The full source list and the open items are in section 9.
